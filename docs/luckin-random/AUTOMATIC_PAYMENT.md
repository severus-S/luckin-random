# 自动付款策略研究

核查日期：2026-11-05。本轮用户要求继续研究自动付款，同时保留“不创建新订单”的约束。这里只记录可验证的产品与接入条件，没有开通钱包、签署代扣、充值、创建订单或发起支付。0.1.1 的官方 App 跳转仍是人工交接，不能算自动付款。

## 新发现与路线优先级

| 路线 | 官方证据及当前条件 | 对本项目的判断 |
|---|---|---|
| 支付宝移动 Agent 的委托任务 | 产品页介绍预设金额、频次与条件后执行，展示瑞幸为合作客户；当前为企业定向邀请试运营 | 最符合预先授权后自动执行的目标，优先核实准入及委托接口；合作展示不能证明本 App 已获权限 |
| 支付宝办公 Agent 钱包 | 官方公开消费者绑定与支付处理源码；支付处理需要支付宝收银台材料或 HTTP 402 支付凭据 | 不同于之前检查的商户收款 MCP，值得单独保留；现有微信 Native QR 不是支付宝订单材料 |
| 微信 AI 专属卡 | 正式文档规定笔笔确认，商户需在传统下单后增加 x402 登记并取得支付凭据 | 可研究减少支付交接，不满足当前“无需每单人工确认”的目标；不能仅凭旧 QR 自行代商户登记 |
| 瑞幸自身免密/余额/咖啡钱包 | 本轮实时订单工具未提供签约、扣款或支付方式参数；用户手机里的实际入口与状态尚待反馈 | 作为个人账号路线继续核查。即使官方 App 已签约，也不能推定该授权对 MCP 创建来源生效 |
| 券抵扣至零元 | 现有预览及创建合同有优惠和 needPay 的概念；没有验证本账号零元履约 | 不是银行卡自动扣款。不能主动消耗权益测试，也不能用零元报价或 needPay=false 单独判定已支付 |

## 本轮实际只读检查

在既有服务器内只读打开 SQLite，令牌仅在服务器内存解密。操作白名单只允许初始化、工具发现、资源列表及提示列表，没有任何业务工具调用。实时返回仍为 8 个工具，资源与提示列表均为空；创建参数只有门店、商品、位置、优惠券和备注，并禁止额外字段，没有支付渠道、代扣协议或 Agent 支付输入。

检查前后配置摘要与官方订单记录数量相同；realOrdersEnabled=false、emergencyStop=true，服务端两项真实创建门禁保持关闭。此证据证明当前公开调用面未提供所需入口，不证明瑞幸内部或合作渠道没有自动付款。原始 schema 和检查结果只留在受保护服务器与本机忽略目录，公开材料不含令牌、真实订单或付款地址。

## 支付宝移动路线的具体接入缺口

[移动端技术文档](https://aipay.alipay.com/docs/agent-pay/mobile-agent-pay.html) 描述的标准链路是：商家生成支付宝预下单标识，平台生成签名串，由客户端 SDK 推进支付，服务端接收结果。它要求已签约对应产品，且说明不支持沙箱。

[接口文档](https://aipay.alipay.com/docs/agent-pay/api-list/agent-pay.html) 将 prepay_id 列为必需字段。现有瑞幸 MCP 订单号、微信 QR 与支付宝预下单标识不是同一种凭据，不可相互替代。

产品页展示委托模式，但本轮查到的公开标准接口仍涉及客户端唤起；没有取得能让本后端在手机锁屏/离线时直接扣款的委托执行接口合同。因此不能据此宣称定时任务已经可以无人值守付款。

正式接入前还需：

1. 确认本应用主体是否符合定向邀请条件，取得应用及智能体身份和对应产品权限。
2. 瑞幸为本 App 提供同一笔订单可用的支付宝预下单材料，以及调用来源、商户身份和订单的绑定规则。
3. 取得委托任务的实际签约、状态查询、执行、撤销、过期和通知接口；明确能否服务端执行，哪些情况仍需手机确认。
4. 首次授权在用户手机的官方流程完成；仅保存受控凭据，不采集支付密码。授权应限定商户、商品/门店、单笔及周期上限、频次、有效期和撤销方式。

以上是待核实条件，不是已取得的资质或已完成的代码接入。

## 微信路线的界限

[微信 AI 支付 FAQ](https://pay.wechatpay.cn/doc/v3/merchant/4035576771) 允许商户将原有预支付标识登记到 AI 支付流程，因此“Native 形式永远不能衔接 AI 支付”过于绝对。但这需要商户的额外接入；本项目没有瑞幸相应身份及登记凭据，不能把用户收到的 QR 当作商户权限。

[产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4035576700) 当前明确逐笔授权；[接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4035576711) 说明商户及 SkillHub 身份要求。一般的[微信委托代扣](https://pay.wechatpay.cn/doc/v2/partner/4011988361) 是另一项需商户权限、模板与用户签约的产品，不会因绑定 AI 专属卡或登录瑞幸而自动获得。

## 能力到位后的实现与验收顺序

1. 先做只读能力/授权状态校验。缺少商家凭据、签约过期、撤销或需补充确认时，停止自动执行并给出准确原因。
2. 价格与优惠仍以官方最新预览为准，同时验证 App 消费限制和官方委托限额；本地开关不能替代支付平台签约。
3. 为一次任务保存订单与支付的唯一请求标识。创建结果不明时只查原请求；付款结果不明时只对账，不切换渠道再次支付或补单。
4. 按正式接口验证签名、商户、应用、订单和金额；以官方支付结果及瑞幸订单状态确认履约。打开 App、回跳、同步受理或 AI 文本都不是支付成功证据。
5. 分别验收授权/撤销/到期、超限、余额不足、重复请求、通知重放、请求超时和进程重启。锁屏及手机离线能力单独实测，不能从 SDK 编译通过推导。
6. 本轮只完成研究。用户另行授权实际消费后才做受限真单；没有沙箱的产品不能以 Mock 测试代替真实支付验收。
